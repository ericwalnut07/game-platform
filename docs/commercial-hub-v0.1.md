# 商都開発 Web試作版 v0.1

4人の人間がオンラインで1ゲームを完走し、ルール・バランス・UI・所要時間を実地検証する試作版。
仮タイトルは「商都開発」、固定 `gameId` は `commercial-hub`。アプリ版は **0.10.0**、ルール版は **0.1**。
目標所要時間60〜90分は未実測。自動テストの完走を人間プレイテストの代わりにはしない。

今回の範囲は実装・検証・PRまで。本番migration、deploy、mainへのマージは別途依頼された場合だけ行う。

## R1〜R8 確定内容

| ID | v0.1正式処理 |
| --- | --- |
| R1 | 建設+1、上位化+1、物流路+1、公共事業完成+3。City Lvはラウンド終了時だけ更新。8/18/28への途中到達でそのラウンドの条件を変えない |
| R2 | 各スート1商機を用意。5/6トリックは追加1/2枠を独立抽選。優先スートを60%で直接選択、残る40%は4スート均等（実効70/10/10/10）。優先なしは各25%。スート内は50/50。重複可。全体をシャッフルして先に公開 |
| R3 | 敷設クレジットは資金→資材の順に自動消費。通常M1+C1なら2点で無料。未使用は繰越。敷設商機、倉庫地区、未接続港湾地区の権利を同じ残高で管理 |
| R4 | 輸送クレジットも繰越。建物の当R限り軽減→輸送クレジットの順に消費。他社網所有者の収入は実際の支払額だけ。同一利用者→所有者の最初の利用が0でもそのRは料金判定済み |
| R5 | 最初の公共事業はLv2になった次Rの開始時。中央市場→中央駅→市庁舎の固定順。完成時に得点・発展+3を反映し、次案件を直ちに公開。案件なしの公共事業商機は影響力2/1。無料貢献は空き枠を選択し、権利を持ち越さない |
| R6 | 同R建設・上位化の能力も使用可、同じ建物は1R1回。収入は工場→工房→ビジネス街販売権→商館→店舗→支店・本社。使用と販売数量は任意。工業団地+1は最初の実生産へ自動適用。地区ボーナスは次R開始時に発動 |
| R7 | 能力は建物ごとに累積。各物流建物の輸送料軽減1/R、各LCの敷設資金軽減1回/R、各本社の影響力支払い軽減1回/Rを別々に管理。未使用分はR末に失効 |
| R8 | Trump→Lead→その他、各カテゴリ内は高ランク優先。同じ強さなら先出し優先。2位のオフスート同ランクにも適用 |

物流センターの敷設軽減は当R限りのため、繰越可能な敷設クレジットより先に資金部分へ適用する。1回の敷設に複数LCを無駄に消費しない。

### 地区ボーナス

同系統の建物をその地区に建てた商会ごとに予約し、次R開始時に一度だけ有効化する。
1商会1地区1建物の制限と合わせて、同じ商会が同じ地区のボーナスを再取得することはない。

| 地区 | 枠 | 効果 |
| --- | ---: | --- |
| 市場地区 | 2 | 資金1を自動取得 |
| 工房地区 | 2 | 商品1を自動取得 |
| 倉庫地区 | 2 | 敷設クレジット1 |
| 官庁地区 | 2 | 影響力1を自動取得 |
| ビジネス街 | 2 | 商品1→資金3の販売権を1回 |
| 工業団地 | 2 | 次の実生産に商品+1 |
| 港湾地区 | 2 | 発動時に自社網接続済みなら資金1、未接続なら敷設クレジット1。その後再判定しない |
| 新市街 | 3 | 次の建設の資金コスト-1 |

旧市街に私有建物枠はない。外周4地区はLv2から建設可能で、影響力1と輸送アクセスが必要。
異系統の建設は可能だが地区ボーナスを得ない。権利型の未使用分は保持する。

### 建物・得点

| 系統 | 基本建物 | 上位建物 |
| --- | --- | --- |
| 工業 | 工房: M1→商品2/R | 工場: M1→商品3+C1/R（実際に資材を使ったときだけC1） |
| 商業 | 店舗: 商品1→C2/R | 商館: 商品を最大2、各C2で販売/R |
| 物流 | 倉庫: 輸送料軽減1/R | LC: 輸送料軽減1/Rと、敷設資金軽減1回/R |
| 市政 | 支店: 影響力1/R | 本社: 影響力1/Rと、影響力支払い軽減1回/R |

M=資材、C=資金。最初の工房はM1+C1、2軒目以降の工房と他の基本建物はM1+C2。上位化は全系統M1+C2。
1系統3軒、全体6軒、同一商会は同一地区1軒まで。

企業価値は基本建物3、上位化追加2、物流路1本1（上限5）、完成公共事業の貢献1枠1と最多ボーナス（単独2/同率各1）、資金4につき1、資材＋商品3につき1。端数切捨て。
25点到達と終了判定はラウンド末。Lv4初到達なら次Rが最終。最終企業価値→資金で比較し、それも同点なら共同勝利。

## 状態遷移と操作

| サーバーフェーズ | 入力と遷移 |
| --- | --- |
| ROUND_START | 情勢・全商機・本人の手札を公開。地区効果と公共事業初公開を処理。4人の確認後にTRICK |
| TRICK | 時計回りに1枚。Must FollowをAPIでも検証。4枚で順位・報酬を処理 |
| REWARD | 販売個数または無料貢献枠の選択が必要な獲得者だけ入力。順に処理 |
| TRICK_RESULT | 1.8秒の自動表示。リードを勝者と独立に1人進め、次トリックまたは投資へ |
| INVESTMENT | 第1巡・第2巡各4人。交渉→公共市場→投資。実行可能な投資があるときはパス不可 |
| INCOME | 各自が指定順の能力使用計画をまとめて確定。4人の確定後に都市Lv・終了判定 |
| ROUND_END | 2.5秒の自動表示後、開始商会を1人進めて次ラウンドへ |
| FINISHED | 企業価値内訳・順位・終了理由・勝者。ホストが同室再戦可能 |

トリックのグローバルリードと投資第1巡の開始商会は独立して保持する。
投資第2巡は第1巡開始商会の左隣から始める。
収入の同時確定は自己資源だけを変えるため、他の商会の確定待ちで入力を無効化しない。

## 実装構成

- Core: `src/games/commercial-hub/`。`engine.ts` が全フェーズ、`investment.ts` が支払い・割引見積、`income.ts` が固定順能力処理、`state.ts` がサーバーState。
- `module.ts` をGameRegistryへ登録。オンライン4人・1ゲーム固定で設定は `{}`。
- `view.ts` は公開項目を列挙する。全員の `playerHands` は送らず、本人の `hand` と他商会の枚数だけ返す。収入プレビュー用データにも他人の手札は含めない。
- `web-actions.ts` は入力フィールドを検証・抽出し、playerIdを既存WebSocketセッションから注入する。クライアントからの `ADVANCE` は拒否。
- 順番入力はラウンド・トリック・出札数・投資巡・手番・交渉段階をphase tokenに含める。古い画面からの遅延操作は既存phaseVersionで拒否。
- requestId二重処理防止、Durable Object保存、再接続、reload、スリープ復帰は共通基盤を利用。交渉相手・提示条件・対案状態も復元する。
- 建物の上位化状態・地区占有は `buildings`、公共事業貢献は案件の `slots`、投資手番は `investmentTurn.playerId` に保持し、重複した正本を作らない。
- UI: `src/client/games/commercial-hub/`。盤面、商機列、手札、交渉、公共市場、投資、収入、事業、企業価値内訳、最終結果、常設ルール。
- モバイルは「手番／都市・事業／商会・履歴」を切替。資源・都市Lv・現在の手番は上部へ。ルールは `/#/rules/commercial-hub`、直接作成は `/#/create/commercial-hub`。
- 『ポンはいない』のCore・得点・結果まとめと別エンディング・マッチ数には変更を加えない。

## D1プレイテストログ

次番号migration `0007_commercial_hub.sql` を追加。既存migrationは変更しない。

| テーブル | 内容 |
| --- | --- |
| playtest_matches | 共通の開始・終了・部屋状態。`game_id='commercial-hub'`、4人、1ゲーム |
| commercial_hub_matches | app_version、rules_version、人数、開始/終了時刻、総R数、終了理由、最終企業価値内訳、勝者、Lv4初到達R、最終revision |
| commercial_hub_events | `game_id='commercial-hub'`、app_version、match_id、連番、R、種類、匿名ゲーム内playerId、公開イベントpayload、記録時刻 |

イベントはサーバーが成功した処理から生成する。生のクライアントpayloadをHubの汎用ログへコピーしない。
`(match_id, sequence)`で重複を防ぎ、summaryはrevisionが新しい書込みのみ反映する。
手札・表示名・セッショントークン・パスワードは保存しない。出したカードは公開済み履歴として保存する。
共通基盤と同様にD1書込みは `waitUntil` で実行する。D1障害中の完全な配送保証は対象外であり、プレイ前にmigrationとログ保存を確認する。
Hubの専用イベント・結果はプレイテスト資料として自動削除しない。既存Pon用分析は `game_id='pon-inai'` に限定する。

保存イベントには以下を含む。

- `TRICK_RESULT` / `OPPORTUNITY_REWARD` / `OPPORTUNITY_SALE`: 順位、商機、公開カード、実販売数。
- `TRADE_OFFERED` / `TRADE_COUNTERED` / `TRADE_ACCEPTED` / `TRADE_REJECTED`: 条件・資源内容。種類ごとの件数が提示数・成立数になる。
- `MARKET_USED`、`BUILD`、`UPGRADE`、`ROUTE`、`TRANSPORT_USED`: 市場・投資履歴、支払額、割引使用、他社網所有者。
- `PROJECT_CONTRIBUTION` / `PROJECT_COMPLETED`: 案件と貢献枠、無料/有料、完成履歴。
- `DISTRICT_BONUS` / `ABILITY_USED` / `DISTRICT_PRODUCTION_BONUS`: 地区取得効果、工場稼働、商館の販売個数など。
- `ROUND_ENDED`: 全商会の資源・企業価値、都市発展度、City Lv、最終ラウンド予約。
- `GAME_FINISHED`: 確定結果。

取得例（環境指定は検証対象に合わせる。本番参照や本番migration/deployを自動的に行わない）:

```sql
SELECT match_id, app_version, started_at, finished_at, total_rounds,
       end_reason, final_values_json, winners_json, city_lv4_round
FROM commercial_hub_matches ORDER BY started_at DESC;

SELECT event_type, COUNT(*) AS count FROM commercial_hub_events
WHERE match_id = :match_id GROUP BY event_type;

SELECT round_number, player_id, payload_json FROM commercial_hub_events
WHERE match_id = :match_id AND event_type IN ('TRADE_OFFERED','TRADE_ACCEPTED','ROUND_ENDED')
ORDER BY sequence;
```
