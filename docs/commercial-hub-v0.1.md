# 商都開発 Web試作 v0.1 実装記録

## 目的・現在の状態

4人の人間がオンラインで1ゲームを完走し、ルール・バランス・UI・所要時間を実地検証するための試作。
仮タイトルは「商都開発」、固定識別子は `commercial-hub`。目標所要時間は60〜90分で、まだ実測していない。

**現在は確定済みCoreの先行実装。オンライン試作版は未完成。**
未確定ルールを仮の数値で固定しないため、GameRegistryとゲーム一覧にはまだ登録していない。
GameModule・ラウンド全体のreducer・UI・D1連携は、下記のルール決定後に実装する。
今回の依頼範囲はPRと検証までで、本番migration・deploy・mainへのマージは行わない。

## ルール決定が必要な点

共通指示§8・§9と今回の引継ぎ§37に従い、以下を実装都合で決めない。
候補はレビュー用の提案であり、採用済みルールではない。

| ID | 未確定・不一致 | 決める内容／候補 |
| --- | --- | --- |
| R1 | 引継ぎ§24に建設・上位化・物流路の発展度加算値がない | 各アクションの加算値。旧代表ログから建設+1・物流路+1が推測されるが、上位化を含む現行値は確定できない。公共事業完成+3は確定 |
| R2 | 追加商機の「やや高確率」の数値がない | 条件に対応するスートの重み、残り3スートの重み、各スート内の2商機の選択確率。重複商機は資料の代表例には存在する |
| R3 | 敷設クレジットの対象と期限がない | 資材・資金のどちらを減らせるか、1点の使用先をプレイヤーが選ぶか、未使用分の繰越。地区の「敷設コスト1軽減」も同じ対象か |
| R4 | 輸送商機は「一時的」だが期限・軽減時の受取額がない | 当R限りか。倉庫等で他社網料金を軽減したとき、所有者への支払額も0か、市が補填するか。0支払いでもその相手への当R支払い済みになるか |
| R5 | 引継ぎは「現在の公共事業」へ無料貢献、Simは最初の公開をLv2としている | 初回公開はゲーム開始時かLv2か。公開前・3件完了後の公共事業商機1位の処理。完成後の次案件をいつ公開するか |
| R6 | 建物能力の使用時期・処理順が不十分 | 工業生産／商業販売を収入・生産フェーズで任意実行するか、所有者が順序を選ぶか、建設したRから使用可能か。地区の販売・生産ボーナスの使用時期と権利の失効も確定する |
| R7 | 同じ系統を複数所有した場合の軽減能力 | 倉庫・物流センター・本社の軽減が建物ごとに重なるか。複数本社の「最初の影響力支払い」は全本社で同じ支払いを指すか |
| R8 | オフスート同ランクで2位が並ぶ場合 | 先出し優先などのタイブレーク。Coreの比較関数は等価を返し、2位の権利を勝手に付与しない |

投資のパスは引継ぎ§12の「実行可能な場合に1回行う」を基準とし、実行可能な投資がある場合は必要な1回を行う設計予定。
ラウンド数の上限や、追加の公共事業恒常効果は導入しない。

## 実装したCore

`src/games/commercial-hub/` に純粋なTypeScriptの部品を配置。

| ファイル | 実装済みの責務 |
| --- | --- |
| types.ts / data.ts | 識別子、型、4系統、5情勢、8商機、9地区、E01〜E16 |
| cards.ts | 32枚デッキ、4人配布、Must Follow、Trump/No Trumpの勝者、時計回り順、投資2巡順、本人だけの手札View |
| resources.ts | 初期資源、資源検証、双方の資源を同時確認する交換、公共市場の価格と1R1回の制限 |
| negotiation.ts | 1相手への提示・承諾・拒否・1対案、対案への再対案拒否、操作権限、交渉→市場→投資の順序 |
| logistics.ts | 旧市街から自社だけで連続する物流網、延伸、1辺1社、1社1スポーク、無軽減時の他社網料金と利用者・所有者ペアの1R上限 |
| buildings.ts | 基礎建設費・配置制約・残り建設数・上位化、選択済み生産／販売／市政収入の1回分の処理とラウンド別使用記録、建物1軒ごとの軽減能力値 |
| opportunities.ts | 商機の1位・2位報酬定義、選択した数量の販売。権利の期限や使い方は決めない |
| projects.ts | 6枠、支払い／無料貢献、累積貢献、完成判定、完成済み貢献と最多ボーナスの得点 |
| scoring.ts | 企業価値内訳、物流路5点上限、Lv閾値、ラウンド末の25点／Lv4翌R終了判定、資金タイブレーク・共同勝利 |

部品の呼び出しだけではWebSocketの認証・requestId・フェーズ検証を実装したことにはならない。
たとえば `produce` は生産の1回分を実行する部品であり、「誰がいつ生産を選択できるか」は未実装。
建設・物流路・上位化の都市発展加算、割引精算、地区ボーナス発火はR1・R3・R4・R6・R7の決定後に接続する。

## 状態遷移・共通基盤への接続予定

| 段階 | 操作・遷移 | サーバーが保持する情報 |
| --- | --- | --- |
| ROUND_START | 情勢・全商機を公開し配布 | round、cityCondition、trump、opportunities、playerHands、global trickLeader |
| TRICK | リードから時計回りに1枚。全員後に順位と報酬処理 | trickIndex、playedCards、手番。商機の数量／枠選択があればその待機状態 |
| INVESTMENT | 2巡・各4人。交渉→市場→1投資 | pass、starter、currentPlayer、negotiationState、marketUsed、resources、buildings、routes、project |
| INCOME_PRODUCTION | 決定したルールに従って能力を処理 | 各建物の使用記録・地区ボーナス |
| ROUND_END | Lv更新、最終ラウンド予約、25点／終了判定 | development、level、values、finalRound、round snapshots |
| RESULT | 得点内訳・順位・勝者、同室再戦 | result、matchId、ログ保存状態 |

- サーバーは `GameRegistry` から新 `GameModule` を取得。既存のRoomObjectの認証済みplayerId、requestId重複防止、Durable Object保存／再接続を使用する。
- `getStateInfo.phase` はラウンド・トリック・投資手番・交渉段階を区別する必要がある。現行RoomObjectはphase文字列が変わるとphaseVersionを更新するため、古い手番からの遅延操作を拒否できるようにする。
- Player Viewは公開フィールドを列挙し、全員の手札を含むStateをspreadしない。交渉もサーバーから復元する。
- 部屋作成・待機部屋・ゲーム画面・ルールへの入口をgameIdで切り替える。商都開発は4人・1ゲーム固定。Pon Inaiの1〜5ゲーム設定は維持。
- モバイルは手番操作・盤面・商会情報をすぐ切り替えられる表示とし、重要情報・手札・次商機へ短い操作で戻れるようにする。
- D1は既存の共通マッチ／イベント表を活用し、商都開発のラウンド・アクション・集計用に次番号のmigrationを追加する予定。ログに手札・表示名・セッショントークンを保存しない。アプリ版とルール版0.1を分離する。
- アプリversionは起動可能なゲームを追加するコミットで更新する。この先行実装ではv0.9.2を維持。
