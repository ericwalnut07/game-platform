# 商都開発 v0.4 — ビッド・監査官・数量選択

アプリv0.15.0。実装前に最新main `e0ca3d53bb1561ac132ebf6fcab3bb5bcce2f571`（v0.14.0／ルールv0.3）を正本としてCore・View・UI・サーバー・テスト・migration・CIを確認。今回の追加は未実装だった。既存のLv1〜4、8地区17枠、最大12R、投資2周、輸送費の後払い、公共事業の段階公開を維持する。

## 設定と進行

部屋作成と開始前ロビーでホストが`trickRule: NORMAL | BID`、`auditor: boolean`を独立に選ぶ。旧来の`{}`も通常＋監査官なしとして解釈する。ゲストへ設定を配信し、既存の設定変更時の準備解除を維持。再戦でも同じ設定を使用する。マップ・最大Rの追加選択肢は設けない。

`ROUND_START`で公開商機と手札を確認後、ビッド時は`BID`へ。全員確定で`TRICK`へ移る。全トリックと即時報酬の完了後、ビッド時は`BID_RESULT`、監査官使用時のR2以降は`AUDITOR_PLACEMENT`、その後`PROCUREMENT → PRODUCTION → INVESTMENT（2周）→ ROUND_END/FINISHED`。自動結果表示は既存と同じ1.2秒のAlarm予約で進行し、予測結果の一覧と履歴は引き続き確認できる。Alarmの実行時刻自体は厳密なリアルタイム保証ではない。

## ビッドと秘匿

- 0〜今Rの総トリック数を同時・非公開で確定。一度確定すると変更不可。合計制限なし。
- Stateの`bids`を公開前にそのままViewへコピーしない。Viewは本人の`ownBid`と確定済みプレイヤーのみを返す。他人の宣言は全員確定まで送信しない。
- `BID_SUBMITTED`の公開イベントに数値を入れない。全員確定時に1回の`BIDS_REVEALED`で全宣言を公開。
- 実際の`ranking[0]`を`trickWins`へ記録し、信用収縮の`rewardRanking`と分離。
- 全トリック後の完全一致は一律＋1、不一致0。`predictionPoints`はRをまたいで累積。企業価値の`prediction`内訳を追加し、事業資産のタイブレークには含めない。

公開後に宣言・実績・残りトリック・可能/不可能・累積点、R別の的中と獲得点を表示する。本人手札・商機順・各商機の切札は宣言中も参照可能。

## 監査官

共通の1コマ。R1には配置しない。R2以降、最後の行政商機の実際の1位を`lastAdministrationWinner`に記録。ビッド結果後に配置権を確定する。8地区または`PUBLIC_PROJECTS`へ確認操作で置く。同じ場所への据え置き可、放棄不可。確定まで旧位置を維持。

地区の建設・上位化・輸送路・建物使用、公共事業全体の拠出1枠に追加資金1。無料拠出・配置者本人も対象。数量に比例させず、銀行へ即時支払い。直接の商機報酬や公共市場に監査費を加えない。割引・無料報酬で監査費を消さず、還元/販売収入を受け取る前に支払能力を検証する。

共通quoteに`normalCost`・`auditFee`・即時`cost`を持たせ、建物と投資の全経路で同じ計算を使う。輸送費は別のR末精算を維持。費用内訳では両方を含む合計も表示する。地区名横の独立アイコンと枠の強調、公共事業全体の明示、スマートフォンの常設コンパクト表示を追加。

## 建物とNPC

物流センターは資金2→資材2を標準、資金1→資材1を少量選択。商館は商品2→資金6を標準、商品1→資金3を少量選択。いずれも少量で1棟1R1回を全部消費する。物流センターの大量仕入れ加算・分配、商館の販促、既存工場の能力値は維持。

共通`BuildingCard`は最大数量を初期選択し、不可能なら合法な少量へ切り替える。数量・輸送方法に応じて費用を再表示する。どれも不可能なら使用不可と不足理由を表示する。

NPCロジック版`0.4.0`。`decideNpc`は本人の`HubView`だけを受け取る。ビッドは本人手札と公開デッキ/商機の勝利数分布から予測し、カード選択は商機報酬・将来商機の温存・予測成功点・最後の行政商機の配置権を複合評価。重みは`NPC_RULE_WEIGHTS`へ分離した。予測は簡易分布モデルで、相手の実際の未公開手札を用いた展開ではない。

開発型は生産・販売基盤を先に確保し、その後は将来使える輸送路と完成見込みのある公共事業を強く評価する。翌Rの販売見込みと投資資金、監査/輸送費を考慮。数量も在庫需要・販売/投資予定・使用1回の固定費を比較する。監査官は他社の見込利用・建設/上位化/路線・公共事業残枠・資金圧力から自社負担を控除し、据え置きも候補とする。係数は性能保証ではなく継続調整対象。

## 通信・運用

GameModuleの既存450ms常設NPCスケジューラと、60秒切断BOTの方針を継続。未確定ビッドと未配置監査官だけを代行し、本人復帰時も確定済み操作は巻き戻さない。requestId、直列処理、再接続、再読み込み、部屋期限/ホスト移譲は共通サーバーを使用。

一般D1ログは公開イベントだけ。設定は`ROUND_STARTED`、全員公開後のビッドと予測結果、監査官確定・各行動の費用を既存JSONへ保存する。任意同意付き詳細ログは本人の非公開ビッドと当時の合法選択肢を本人/NPCの記録へ追加し、他人の未公開ビッドを公開スナップショットへ入れない。既存同意・削除・保持・管理認証を維持。schema変更と新規migrationは不要。maintenanceと`/api/health`は共通仕様を維持。

本番更新はこの実装の承認とは分ける。v0.3の進行中Stateを途中変換しない既存方針を維持するため、次回本番公開前に旧ゲームを終了する。今回本番deploy・remote D1 migration・Secret変更を実行しない。

## 検証

Unitは設定4通り・秘匿/二重確定・信用収縮・得点累積・最後の行政商機・据え置き/放棄拒否・切断代行/復帰・全監査費・無料/還元拠出・資金不足・数量/使用制限・表示とNPC公開情報境界を確認。Durable Objectテストは同時確定、全員公開、認証されたactor、hibernation後の再送、配置/費用の冪等性を確認する。

E2Eは4人の設定同期、非公開確定と再読み込み、候補未確定/確定、PC/スマートフォンの表示、ビッド＋監査官の人間1/NPC3混合戦を含む。通常4人対戦とポンはいない等の既存回帰も継続。

再現比較：`npm run simulate:hub-rules -- --games=100 --seed=7823 --output=fixed.json`。各条件100局、同じ25シードを4席順で回し、全4条件を対応させる。別基点`1040213`でも同じ構成で再検証する。通常NPCシミュレーションと16局の4条件smokeも`npm run verify`に含める。詳細値と測定上の限界は[検証報告](commercial-hub-v0.4-validation.md)を参照。
